## 1. 왜 이 문서가 필요한가

테이블 목록은 있었다. 없던 것은 **불변식**이다 —
유니크 제약을 왜 유저 범위로 걸어야 하는지, `ON DELETE CASCADE` 에 왜 기대지 않는지,
표를 더할 때 왜 `OWNED` 목록을 같이 고쳐야 하는지가 **전부 코드 주석에만** 있었다.
주석은 그 파일을 여는 사람만 읽는다. 새 표를 만드는 사람은 `models.py` 는 열지만
`services/account.py` 는 열지 않는다.

그리고 회원 데이터 격리를 지키는 검사가 **히스토리 읽기 하나**뿐이었다.
나의 표현 · 연습 기록 · 데이터 삭제는 동작은 맞았지만 **아무것도 지키고 있지 않았다.**
이 저장소 기준으로 그건 없는 것과 같다.

## 2. 소유 모델

표는 **둘로만 갈린다.**

```
users                       주인.  한 행이 한 회원
  ├── analyses              매달린 표. 전부 user_id 를 든다
  ├── practices
  ├── vocabulary
  └── usage_counters
```

| 테이블 | 내용 |
|---|---|
| `users` | Google 식별자, 이메일, 동의 시각, 암호화된 API 키 |
| `analyses` | 분석 히스토리 (기기 간 동기화) |
| `practices` | 작문 연습 채점 기록 |
| `vocabulary` | 나의 표현 (화면에서 부르는 이름만 다르다 — [03](03-api-spec.md)) |
| `usage_counters` | 일 단위 사용량 |

**매달린 표의 목록은 코드에도 있다** — `app/services/account.py` 의 `OWNED`.
그 상수가 삭제·집계·탈퇴에 쓰이므로, **목록이 불완전하면 탈퇴한 회원의 데이터가 남는다.**
`→ backend/app/services/account.py`

로컬 모드도 같은 표를 쓴다. 앱이 뜰 때 만드는 사용자 행 하나(`id=1`)가 주인이다.
**두 모드가 같은 스키마를 쓰므로 리비전도 하나다** ([09 §4](09-mode-matrix.md)).

## 3. 불변식 여섯

각 항목에 **짝지은 장치**가 있다. 없으면 그건 부탁이다.

### 3.1 모든 질의는 `user_id` 로 좁힌다

꼴은 셋뿐이다.

```python
db.query(Model).filter(Model.user_id == user.id)       # 목록 · 집계
db.get(Model, id)  →  row.user_id != user.id 면 거부    # 단건
delete(Model).where(Model.user_id == user_id)           # 삭제 · 탈퇴
```

**단건 조회가 가장 위험하다.** `db.get` 은 id 만 보므로 소유자 확인을 빼먹으면
**남의 기록 id 를 찍어 읽을 수 있다.** 그래서 `db.get` 뒤에는 반드시 확인이 붙는다.

없는 기록과 남의 기록을 **같은 오류로** 돌려준다 — 둘 다 `404 not_found` 이고
**메시지도 같다.** 다르게 답하면 id 를 훑어 "있는지 없는지"를 알아낼 수 있다.
404 와 403 을 나눠 주면 "403 이 떴다 = 그 번호가 존재한다" 가 되고, 내용을 못 봐도
다른 회원이 몇 건을 쌓았는지 셀 수 있다. 상태 코드만 맞추고 메시지로 갈리는 것도
같은 누출이므로 **본문까지** 같은지 검사한다 ([03](03-api-spec.md), H-012).

### 3.2 유니크 제약은 유저 범위다

```
uq_vocab_user_expression  (user_id, expression)
uq_usage_user_day         (user_id, day)
```

**`expression` 만으로 걸면 한 회원이 담은 표현을 다른 회원은 못 담는다.**
전역 유니크는 이런 버그를 조용히 만든다 — 먼저 담은 회원에게는 아무 일도 안 일어나고,
나중 회원만 실패한다. 매달린 표의 유니크 제약에는 **반드시 `user_id` 가 들어간다.**

### 3.3 지울 때 `ON DELETE CASCADE` 에 기대지 않는다

FK 에 `CASCADE` 를 적어 두었지만 **코드는 표마다 명시적으로 지운다.**

SQLite 는 `PRAGMA foreign_keys` 가 꺼져 있으면 CASCADE 가 안 돈다. 테스트는 SQLite 로
도므로, 기대면 **테스트는 통과하고 Postgres 에서만 다르게 도는** 상태가 된다.
그 방향의 어긋남은 배포본에서야 드러난다.

### 3.4 표를 더하면 `OWNED` 에 더한다

새 표가 `user_id` 를 들었는데 `OWNED` 에 없으면, 그 표는
**데이터 삭제에도 탈퇴에도 안 걸린다.** 회원은 "전부 지웠다" 는 답을 받고
데이터는 남는다. 개인정보 관점에서 가장 나쁜 종류의 버그다.

### 3.5 저장된 형식은 읽을 때 올린다

프롬프트를 손볼 때마다 결과 스키마가 바뀌고, DB 에는 그때그때의 형식으로 저장돼 있다.
**검증을 느슨하게 해서 해결하지 않는다** — 같은 Pydantic 모델이 LLM 응답 검증에도
쓰이므로, 모델이 필드를 빠뜨려도 조용히 통과하게 된다.

그래서 모델은 엄격하게 두고 `app/services/records.py` 가 **읽을 때만** 올린다.
새로 저장하는 기록에는 `schema_version` 을 남긴다. 경위는 [07 §8.1](07-web-deployment.md).

### 3.6 `vocabulary` 와 `practices` 는 `(user_id, expression)` 으로 이어진다

외래키가 아니다. **연습 기록이 먼저 쌓여 있었기 때문**이다 — 옮겨 붙이려면 짝을 못 찾는
행을 버리게 된다. `unique(user_id, expression)` 이 이미 걸려 있어 자연키로 충분하다.

이 연결 때문에 **연습하면 자동으로 나의 표현에 올라가고, 제외하면 기록도 함께 사라진다.**
나의 표현이 연습 기록으로 가는 유일한 입구이므로, 둘을 따로 두면 **어느 화면에도 안
나타나는 유령 데이터**가 생긴다. 근거는 [06 §3](06-practice.md).

## 4. 표를 더하거나 고칠 때

```
1  models.py 를 고친다 — user_id 를 들면 FK(users.id) · index · CASCADE 를 함께
2  user_id 를 들었다면 services/account.py 의 OWNED 에 더한다        (3.4)
3  유니크 제약이 필요하면 user_id 를 반드시 포함시킨다               (3.2)
4  라우터·서비스의 질의를 user_id 로 좁힌다                          (3.1)
5  alembic revision --autogenerate                                   (07 §6.5)
6  pytest — 2·3·4 를 빼먹으면 test_data_layer.py 가 잡는다
```

**2번과 3번이 가장 잘 빠진다.** 빼먹어도 그 표만 쓰는 기능은 멀쩡히 동작하고,
드러나는 것은 **탈퇴할 때**와 **두 번째 회원이 올 때**다. 둘 다 개발 중에는 안 일어난다.

## 5. 불변식마다 짝지은 장치

| 불변식 | 장치 |
|---|---|
| 3.1 질의가 `user_id` 로 좁혀진다 | `test_data_layer.py` — 소유 모델을 쓰는 함수를 AST 로 전수 조사 |
| 3.1 남의 데이터에 손이 닿지 않는다 | `test_data_layer.py` — 소유 엔드포인트 전부를 두 회원으로 찔러 본다 |
| 3.2 유니크 제약이 유저 범위다 | `test_data_layer.py` — 메타데이터에서 제약을 읽어 본다 |
| 3.3 명시적으로 지운다 | `test_both_modes.py` — 삭제가 실제로 0건을 남기는지 |
| 3.4 `OWNED` 가 완전하다 | `test_data_layer.py` — `user_id` 를 든 모델 전부가 목록에 있는지 |
| 3.5 읽을 때 올린다 | `test_both_modes.py` — 옛 형식 기록을 열어 본다 |
| 3.6 제외하면 기록도 사라진다 | `test_both_modes.py` — 연쇄 삭제와 표현 경계 |
| 모델과 리비전이 어긋나지 않는다 | `test_migrations.py` — `compare_metadata` |
| 이 문서의 2절 표 | `test_data_layer.py` — 실제 테이블 목록과 대조 |

**2절 표를 고치면 검사가 깨진다.** 그래서 이 문서는 설명이 아니라 명세다.
