# 12. 도구 규약

> **층** 규약 · **상태** 유효 · **강제** `backend/tests/test_doc_references.py`
> **읽어야 할 때** **검사·생성 도구를 새로 만들거나 고칠 때 — 코드를 쓰기 전에**
> **위** [문서 지도](00-index.md) · **함께** [10 코드 규약](10-code-conventions.md) · [11 문서 아키텍처](11-docs-architecture.md)

이 프로젝트의 규약은 대부분 도구가 지킨다 ([11 §3.4](11-docs-architecture.md)).
그런데 **그 도구를 어떻게 만들고 어디에 등록하는지**가 어디에도 없어서, 만들 때마다
추측으로 만들었다. 그 판단을 여기 고정한다.

## 1. 하나의 구현, 여러 입구

```
0  구현        backend/tools/<name>.py          순수 함수 + main(). stdlib 우선
1  고정        backend/tests/test_<name>.py     규칙을 테스트가 붙든다
2  입구        ./dev.sh <verb>                  유일한 실행 경로
3  강제        CI 스텝                          어기면 머지가 안 된다
4  지침        CLAUDE.md(추상) · README(구체)    언제 쓰는가
5  자동화      훅 · 슬래시 커맨드               잊지 않게 (선택)
```

**0~4 는 거의 항상 다 한다.** 사람에게도, CI 에게도, 어떤 에이전트에게도 통한다.
**5 는 선택이고, 1~4 의 대체가 아니다.** 특정 도구 환경 안에서만 통하기 때문이다.

## 2. 도구는 저장소 안에서 돈다

```
.venv/bin/python tools/<name>.py   지금 이 체크아웃을 읽는다
uv tool install                    ~/.local/bin 에 복사본을 심는다
```

저장소의 문서와 코드를 읽는 도구는 **저장소와 같이 움직여야 한다.** 심어 둔 복사본이
체크아웃보다 뒤처지면 그 순간 갈라진 둘이 되고, 갈라진 둘은 틀린 하나보다 나쁘다
([11 §2.1](11-docs-architecture.md)).

진짜 CLI 가 필요하면 `uv tool` 이 아니라 `pyproject.toml` 의 `[project.scripts]` 를 쓴다.
다만 `./dev.sh <verb>` 대비 이득이 거의 없고 **입구가 둘이 되는 비용**이 생긴다.

## 3. 도구가 지켜야 할 것

### 3.1 읽는 도구와 쓰는 도구를 가른다

쓰는 도구는 **반드시 두 모드**다.

```
./dev.sh ptr            검사만 한다. 어긋나면 exit 1      ← CI 는 이것만 쓴다
./dev.sh ptr --write    실제로 고친다                      ← 사람·에이전트만
```

`gofmt -l` 과 `gofmt -w` 의 관계다. **CI 에서 자동 수정하면 아무도 생성물을 안 본다.**

### 3.2 종료 코드가 계약이다

`0` 은 깨끗, `1` 은 할 일 있음. 셸·CI·에이전트가 전부 이것만 본다.
메시지 형식을 바꿔도 되지만 종료 코드는 못 바꾼다.

### 3.3 멱등

두 번 돌려 결과가 같아야 "검사 = 생성 결과와 같은가" 가 성립한다. **테스트로 붙든다.**

### 3.4 출력은 그 자리에서 고칠 수 있게

`파일:줄`, 그리고 **고치는 명령 한 줄.**

```
  갱신이 필요하다: backend/app/config.py
  → python tools/docptr.py --write
```

### 3.5 생성물의 소유권을 명시한다

docstring 의 `[문서]` 줄은 도구 것, 나머지는 사람 것. **경계가 흐리면 둘 다 안 믿는다.**

### 3.6 주소는 이름으로 쓴다

줄 번호는 코드를 한 줄만 옮겨도 거짓이 된다. qualname 을 AST 로 푼다.
**이름이 바뀌면 실패하는 것이 맞다** — 가리키던 것이 실제로 없어졌으니까.

### 3.7 메타 도구의 함정 둘

문서나 코드를 읽는 도구는 **자기 자신과 자기를 설명하는 문서까지 읽는다.**
둘 다 실제로 밟았다.

```
자기 자신 제외      도구 설명문의 마커 예시를 "지울 마커" 로 봤다
코드 블록 무시      규약 문서가 자기 예시를 가리켜 살아 있는 포인터가 됐다
```

**예시는 코드 블록 안에 적는다.** 이 문서가 그렇게 적는 이유다.

## 4. 어디에 등록하나

| 묻는 것 | 그렇다면 |
|---|---|
| 사람도 쓰나 | `dev.sh` + README **(항상)** |
| 매번 지켜져야 하나 | **CI 스텝** |
| 잊으면 안 되는 규칙인가 | **CLAUDE.md 규칙** — 추상 한 줄, 명령 이름은 예시에 |
| 자동으로 돌아야 하나 | 훅 |
| 자주 치는 질의인가 | 슬래시 커맨드 |
| 외부 서비스·구조화 입출력 | MCP — 거의 아니다 |

**CI 와 훅은 역할이 다르다.** CI 는 **구멍을 막고**, 훅은 **창을 좁힌다.**
CI 가 있으면 어긋난 채로 머지되지 않는다. 훅은 그 위에서, 어긋난 상태로 보내는
시간을 없앤다 — 그 사이에 틀린 생성물을 읽고 믿을 수 있기 때문이다.
**순서는 CI 가 먼저다.** 훅만 있으면 그 환경 밖에서는 아무것도 지켜지지 않는다.

## 5. 새 도구를 추가하는 절차

```
1  태그를 먼저 만든다          M-T 또는 H. 없으면 시작하지 않는다
2  tools/<name>.py            main() + 종료 코드
3  test_<name>.py             규칙 고정 + 일부러 깨뜨려 실패를 본다
4  dev.sh                     case 분기 + 파일 머리 주석 (help 가 그걸 뿜는다)
5  CI 스텝                    검사 모드만
6  README 표 · CLAUDE.md      규칙은 추상, 명령 이름은 예시에
7  11 §3.4 장치 표 · 7절      무엇을 강제하는지 한 줄
```

**4번에서 머리 주석을 빼먹기 쉽다.** `ptr` 를 `case` 에만 넣고 `help` 를 안 고쳐
한 마일스톤 동안 목록에 없었다. 7절 표가 그걸 잡는다.

## 6. 장치는 어긋난 적 있는 규약에만 붙인다

도구를 먼저 만들고 쓸 곳을 찾으면 유지 비용만 늘고 아무도 안 믿는다.
`./dev.sh docs` 는 H-011 과 H-014 가 **실제로 난 뒤에** 만들었고,
`./dev.sh next` 는 `[~]` 네 개를 놓친 뒤에(H-018) 만들었다.

**아직 한 번도 어긋나지 않은 규약에는 장치를 붙이지 않는다.**

**화면도 장치를 붙일 수 있다.** 오래 "프론트는 사람이 본다" 고 적어 두었는데,
그건 검사할 수 없다는 뜻이 아니라 **검사 러너가 없다는 뜻**이었다. 별이 `☆`/`★` 로
갈리는지, 확인 상자가 뜰 때와 안 뜰 때가 규칙대로인지는 DOM 에 다 들어 있다.
보이는 모양(색 · 여백 · 다크 모드)만 사람 몫으로 남는다 — 그 경계를 긋고 나니
사람이 봐야 할 것이 훨씬 줄었다 (M3-T4).

같은 이유로 **도구는 한 번에 완성되지 않는다.** `./dev.sh next` 는 처음에 `[~]` 줄에
"머지됐는지 확인하고 `[x]` 로 올린다" 를 찍었다. 그건 장치가 아니라 부탁이었고,
지켜지지 않았다 — 머지가 브랜치 끝을 안 담은 것을 아무도 못 봤고 배포본이 반쪽이 됐다(H-022).
그래서 지금은 **사람에게 묻지 않고 git 에 묻는다.** 부탁을 한 줄 적어 두는 것으로
끝냈다면, 같은 사고가 다음에도 똑같이 났을 것이다.

## 7. 지금 있는 도구

| 명령 | 무엇을 보나 | CI |
|---|---|---|
| `./dev.sh docs` | 문서 그래프 · 주소 · 머리말 · 색인 · 태그 | 돈다 |
| `./dev.sh ptr` | 문서 → 코드 포인터와 그 역참조 (`--write` 로 갱신) | 검사 모드만 |
| `./dev.sh next` | 열린 작업 (ROADMAP + ISSUES) · `[~]` 가 정말 머지됐는지 | 안 돈다 — 질의 도구다 |
| `./dev.sh check` | llama-server 연결 | 안 돈다 — 환경 확인이다 |
| `npm test` (frontend) | 화면에 그려진 DOM — 별 · 확인 상자 · 기록 펼치기의 규칙 | 돈다 |

이 표의 명령이 `dev.sh` 의 분기와 `help` 목록에 다 있는지는
`backend/tests/test_doc_references.py` 가 본다.
