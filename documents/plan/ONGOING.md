# ONGOING

> **층** 진행 · **상태** 유효 · **강제** `backend/tests/test_doc_references.py`
> **읽어야 할 때** **진행 중인 일을 집거나 놓을 때.** 남이(또는 내일의 내가) 이어받을 때
> **위** [문서 지도](../00-index.md) · **함께** [ROADMAP](ROADMAP.md) · [ISSUES](ISSUES.md) · [DONE](DONE.md)

**지금 열려 있는 일의 세부.** `[~]` 인 태그만 여기 있고, 끝나면 [DONE](DONE.md) 으로
옮기고 이 문서에서 **지운다.**

```
ROADMAP · ISSUES   [ ]  한 줄.  무엇을 할지만
      ↓ 시작하면서  [~]
ONGOING            진행하면서 적는다.  계속 고친다
      ↓ 끝나면     [x]
DONE               무엇을 / 왜 / 어떻게.  **다시 고치지 않는다**
설계 문서           판단이 반영된다.  계속 유효하다
```

## 왜 이 문서가 필요한가

전에는 세부를 둘 자리가 **DONE 뿐**이었다. 그런데 DONE 은 **끝난 뒤에** 쓰는 문서다.
그래서 아직 안 한 일의 세부는 **어디에도 없었고**, 한 줄 요약이 그 역할을 떠맡았다.

한 줄은 길이가 모자란 게 아니라 **틀려도 맞아 보인다.** 실제로
`M2-T1 작문 연습 결과를 저장 — 지금은 채점하고 버린다` 가 그랬다. 저장은 **이미 되고
있었는데**, 그 한 줄이 그럴듯해서 아무도 의심하지 않았다. 코드를 읽고서야 알았다.

그래서 이 문서의 첫 칸이 **전제**다. "지금 어떻게 돼 있나" 와 **어디서 확인했나**를
함께 적는다. 확인 출처가 없는 전제는 짐작이고, 짐작은 조용히 낡는다.

## 형식

```
### <태그> · <한 줄 요약>
시작 <날짜> · 갱신 <날짜>

- **전제** 지금 어떻게 돼 있나. **어디서 확인했나**를 함께 적는다
- **결정** 무엇을 하기로 했나, 왜. 버린 안도 적는다
- **막힌 것** 못 가는 이유 — 물어야 할 것, 재야 할 것
- **다음 걸음** 바로 다음에 할 하나
```

네 칸을 다 채울 필요는 없다. 다만 **전제와 다음 걸음**은 비워 두지 않는다 —
그 둘이 없으면 내일 이어받을 수 없다.

### M13-T4 · 하루 한 번 고른다
시작 2026-10-23 · 갱신 2026-10-23

- **전제** 고르는 **규칙**은 `M13-T1` 에서 실측으로 이미 풀렸다 (DONE 의 표).
  남아 있던 것은 **언제 도나**였다. 두 모드가 정반대라서다 —
  local 은 내 PC 라 꺼져 있을 수 있고, cloud 는 Render 무료 티어라
  **15분 미사용이면 잠든다** (`M3-T3`). 어느 쪽도 상주 스케줄러를 못 믿는다.

- **결정 (사용자)** **시계에 걸지 않는다. 요청이 방아쇠다.**

  ```
  요청이 들어온다
    오늘 것이 있나?
      있다  →  그걸 보여준다
      없다  →  고르기+분석을 시작하고, **그동안 어제 것을 보여준다**
  ```

  켜져 있든 수시로 내려가 있든 같은 코드가 돈다. **늦게 도는 것은 괜찮다** —
  하루에 한 번만 성공하면 되고, 그 전까지는 어제 것이 빈 화면을 막는다.
  cron 도, 상주 프로세스도, 배포 전 단계도 필요 없다.

- **결정 (사용자) — 실패하면 쉰다.** 실패 시각을 **적어 두고, 그로부터 5분
  이내에는 다시 시도하지 않는다.**

  처음에는 "하루 시도 횟수 상한" 을 생각했는데 **그쪽이 나쁘다** — 상한을 다 쓰면
  그날은 포기이고, 문제가 10분 만에 풀려도 내일까지 글감이 없다. 쿨다운은
  **풀리는 순간 저절로 회복된다.**

- **따라 나오는 것 다섯**
  1. **"완료됐나" 는 열로 안 든다.** **문단마다 분석이 있는지로 센다.** 열을 두면
     실제 상태와 어긋날 수 있지만 세는 쪽은 언제나 맞다. 18문단이라 싸다.
  2. **그런데 실패 기록은 열로 들어야 한다.** 메모리에 두면 **안 된다** —
     Render 는 15분마다 잠들고, 깨어날 때마다 쿨다운을 잊고 즉시 재시도한다.
     **막으려던 바로 그 상황에서 안 막힌다.** 그러니 DB 에 남긴다.
     `M13-T4` 에서 작은 공용 표 하나를 더한다 — `(날짜, 출처)` 마다 마지막 실패
     시각과 누적 횟수. **그때 만든다. 쓰는 코드보다 먼저 만들지 않는다.**
  3. **동시 요청은 이미 막혀 있다.** 둘이 동시에 "오늘 것이 없네" 를 봐도
     `uq_article_day_source` 가 둘째 삽입을 거부하고, 문단별 분석도
     `uq_analysis_paragraph_level` 이 겹침을 거부한다 (`M13-T2`).
     **제약이 그대로 잠금 역할을 한다.**
  4. **요청을 막으면 안 된다.** 고르기+분석은 문단 수만큼 LLM 호출이라 수십 초다.
     응답 경로에서 돌리면 첫 방문자가 그 시간을 전부 기다린다. 던져 놓고
     **즉시 어제 것을 돌려준다.**
  5. **재시도는 이어서 한다.** 문단별 분석이 각자 한 행이고 유니크가 걸려 있어
     **이미 끝난 문단은 건너뛴다.** 그래서 5분 뒤 재시도가 처음부터 다시 돌지
     않는다 — 분석 도중에 끊긴 경우의 비용이 재시도 횟수에 비례하지 않는다.

- **쿨다운 5분의 성질** 하루 최대 288번. 가져오기 단계에서 실패하면 LLM 을 안
  부르므로 싸고, 분석 도중 실패는 위 5번 때문에 남은 문단만 다시 돈다.
  **5분은 설정값이 아니라 상수로 둔다** — 바꿀 이유가 생기면 그때 꺼낸다.

- **다음 걸음** `M13-T3`(문단 쪼개기) → `M13-T5`(미리 분석) → `M13-T6`(화면)을
  먼저 한다. 기사 하나를 손으로 넣어 두면 그 셋이 전부 돌아가고 **눈으로 확인할
  수 있는 것이 먼저 나온다.** 자동 선정은 그 위에 얹는다.
