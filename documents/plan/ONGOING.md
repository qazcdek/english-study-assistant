# ONGOING

> **층** 진행 · **상태** 유효 · **강제** `backend/tests/test_doc_references.py`
> **읽어야 할 때** **진행 중인 일을 집거나 놓을 때.** 남이(또는 내일의 내가) 이어받을 때
> **위** [문서 지도](../00-index.md) · **함께** [ROADMAP](ROADMAP.md) · [ISSUES](ISSUES.md) · [DONE](DONE.md)

**지금 열려 있는 일의 세부.** `[~]` 인 태그만 여기 있고, 끝나면 [DONE](DONE.md) 으로
옮기고 이 문서에서 **지운다.**

```
ROADMAP · ISSUES   [ ]  한 줄.  무엇을 할지만
      ↓ 시작하면서  [~]
ONGOING            진행하면서 적는다.  계속 고친다
      ↓ 끝나면     [x]
DONE               무엇을 / 왜 / 어떻게.  **다시 고치지 않는다**
설계 문서           판단이 반영된다.  계속 유효하다
```

## 왜 이 문서가 필요한가

전에는 세부를 둘 자리가 **DONE 뿐**이었다. 그런데 DONE 은 **끝난 뒤에** 쓰는 문서다.
그래서 아직 안 한 일의 세부는 **어디에도 없었고**, 한 줄 요약이 그 역할을 떠맡았다.

한 줄은 길이가 모자란 게 아니라 **틀려도 맞아 보인다.** 실제로
`M2-T1 작문 연습 결과를 저장 — 지금은 채점하고 버린다` 가 그랬다. 저장은 **이미 되고
있었는데**, 그 한 줄이 그럴듯해서 아무도 의심하지 않았다. 코드를 읽고서야 알았다.

그래서 이 문서의 첫 칸이 **전제**다. "지금 어떻게 돼 있나" 와 **어디서 확인했나**를
함께 적는다. 확인 출처가 없는 전제는 짐작이고, 짐작은 조용히 낡는다.

## 형식

```
### <태그> · <한 줄 요약>
시작 <날짜> · 갱신 <날짜>

- **전제** 지금 어떻게 돼 있나. **어디서 확인했나**를 함께 적는다
- **결정** 무엇을 하기로 했나, 왜. 버린 안도 적는다
- **막힌 것** 못 가는 이유 — 물어야 할 것, 재야 할 것
- **다음 걸음** 바로 다음에 할 하나
```

네 칸을 다 채울 필요는 없다. 다만 **전제와 다음 걸음**은 비워 두지 않는다 —
그 둘이 없으면 내일 이어받을 수 없다.

### H-032 · 검사와 cloud 개발이 운영과 다른 엔진에서 돈다
시작 2026-10-23 · 갱신 2026-10-23

- **전제** 네 군데서 DB 를 띄우는데 **운영만 Postgres** 다.

  | 어디 | 엔진 | 확인한 곳 |
  |---|---|---|
  | 단위 검사 (로컬) | SQLite | `tests/conftest.py` · `tests/modes.py` |
  | CI | SQLite | `.github/workflows/ci.yml` — 서비스 컨테이너가 없다 |
  | local 모드 띄우기 | Postgres 17 (도커 15432) | `app/config.py` 의 기본값 |
  | cloud 모드 띄우기 | SQLite | `backend/.env.cloud` 의 `DATABASE_URL` |
  | 운영 (Render) | Neon Postgres | `07-web-deployment.md` |

  **이미 두 번 물렸고, 둘 다 글로 막아 뒀다.** `String` 길이를 SQLite 는 무시하고
  Postgres 는 `value too long` 으로 거부한다 (`tests/test_migrations.py` 의
  주석), SQLite 는 `PRAGMA foreign_keys` 가 꺼져 있으면 CASCADE 가 아예 안 돈다
  (`14-data-layer.md §3.3`). 둘 다 "그러니 조심해라" 로 끝난다 —
  **선언이고 장치가 아니다** (`12-tooling.md §6`).

  주석도 이미 어긋나 있었다. `app/db/session.py` 와 `app/main.py` 가
  "local 은 docker Postgres, cloud 는 Neon" 이라고 적는데 `.env.cloud` 는 SQLite 다.

- **결정** 세 층을 **다르게** 다룬다. 전부 Postgres 로 바꾸지 않는다.

  1. **검사는 양쪽에서 돈다.** 기본은 SQLite 로 두고 (빠르고 오프라인에서 돈다),
     `TEST_DATABASE_URL` 이 있으면 그 Postgres 에서 돈다. **CI 가 Postgres 쪽을
     맡는다** — 머지 게이트가 운영 엔진을 보는 것이 핵심이고, 로컬 반복 속도는
     그대로 둔다. 둘 다 돌리려면 `./dev.sh test --pg`.
  2. **격리는 스키마로 한다.** 테스트마다 DB 를 만들면 느리고, 하나를 공유하면
     서로의 행을 지운다. URL 에 `options=-csearch_path%3D<스키마>` 를 실어
     테스트마다 스키마 하나를 만들고 끝나면 지운다 — **쳐 보고 확인했다**
     (두 스키마가 같은 이름의 표를 각자 들고 서로를 못 본다).
  3. **cloud 모드 띄우기는 Neon 의 별도 브랜치로** 옮긴다. 도커 Postgres 로도
     엔진은 맞지만 **버전·연결 수 제한·콜드 스타트가 다르다.** 같은 서비스의
     브랜치면 그것까지 같아진다.

  **운영 저장소를 가리키지 않는다.** 앱은 뜰 때 `upgrade head` 를 돌리고
  (`app/db/migrate.py`), 개발 중에는 `downgrade` 도 돈다 — 운영 DB 에 걸면
  회원 데이터가 사라진다.

  **문서도 같이 어긋나 있었다.** `07-web-deployment.md §6.4` 가 cloud 를 띄우는
  방법으로 `sqlite+pysqlite:///./local-cloud.db` 를 안내하고 있었다 — 결정 3항과
  정면으로 반대고, `./dev.sh cloud` 의 장치가 **거부하는 것**을 적어 둔 셈이다.
  `09 §6.4` 를 쓸 때 짝을 못 찾았다 (`CLAUDE.md §5.1-7`). 고쳐서 `09` 를 가리키게 했다.

- **다음 걸음** 사용자가 Neon 에 `dev` 브랜치를 만들어 `.env.cloud` 의
  `DATABASE_URL` 을 바꾼다 — 절차는 `07-web-deployment.md §6.4`.
  그 뒤 cloud 모드를 띄워 두 모드를 모두 확인한다.

### M13-T4 · 하루 한 번 고른다
시작 2026-10-23 · 갱신 2026-10-23

- **전제** 고르는 **규칙**은 `M13-T1` 에서 실측으로 이미 풀렸다 (DONE 의 표).
  남아 있던 것은 **언제 도나**였다. 두 모드가 정반대라서다 —
  local 은 내 PC 라 꺼져 있을 수 있고, cloud 는 Render 무료 티어라
  **15분 미사용이면 잠든다** (`M3-T3`). 어느 쪽도 상주 스케줄러를 못 믿는다.

- **결정 (사용자)** **시계에 걸지 않는다. 요청이 방아쇠다.**

  ```
  요청이 들어온다
    오늘 것이 있나?
      있다  →  그걸 보여준다
      없다  →  고르기+분석을 시작하고, **그동안 어제 것을 보여준다**
  ```

  켜져 있든 수시로 내려가 있든 같은 코드가 돈다. **늦게 도는 것은 괜찮다** —
  하루에 한 번만 성공하면 되고, 그 전까지는 어제 것이 빈 화면을 막는다.
  cron 도, 상주 프로세스도, 배포 전 단계도 필요 없다.

- **결정 (사용자) — 실패하면 쉰다.** 실패 시각을 **적어 두고, 그로부터 5분
  이내에는 다시 시도하지 않는다.**

  처음에는 "하루 시도 횟수 상한" 을 생각했는데 **그쪽이 나쁘다** — 상한을 다 쓰면
  그날은 포기이고, 문제가 10분 만에 풀려도 내일까지 글감이 없다. 쿨다운은
  **풀리는 순간 저절로 회복된다.**

- **따라 나오는 것 다섯**
  1. **"완료됐나" 는 열로 안 든다.** **문단마다 분석이 있는지로 센다.** 열을 두면
     실제 상태와 어긋날 수 있지만 세는 쪽은 언제나 맞다. 18문단이라 싸다.
  2. **그런데 실패 기록은 열로 들어야 한다.** 메모리에 두면 **안 된다** —
     Render 는 15분마다 잠들고, 깨어날 때마다 쿨다운을 잊고 즉시 재시도한다.
     **막으려던 바로 그 상황에서 안 막힌다.** 그러니 DB 에 남긴다.
     `M13-T4` 에서 작은 공용 표 하나를 더한다 — `(날짜, 출처)` 마다 마지막 실패
     시각과 누적 횟수. **그때 만든다. 쓰는 코드보다 먼저 만들지 않는다.**
  3. **동시 요청은 이미 막혀 있다.** 둘이 동시에 "오늘 것이 없네" 를 봐도
     `uq_article_day_source` 가 둘째 삽입을 거부하고, 문단별 분석도
     `uq_analysis_paragraph_level` 이 겹침을 거부한다 (`M13-T2`).
     **제약이 그대로 잠금 역할을 한다.**
  4. **요청을 막으면 안 된다.** 고르기+분석은 문단 수만큼 LLM 호출이라 수십 초다.
     응답 경로에서 돌리면 첫 방문자가 그 시간을 전부 기다린다. 던져 놓고
     **즉시 어제 것을 돌려준다.**
  5. **재시도는 이어서 한다.** 문단별 분석이 각자 한 행이라 **끝난 문단은
     건너뛴다.** 5분 뒤 재시도가 처음부터 다시 돌지 않는다 — 분석 도중에 끊긴
     경우의 비용이 재시도 횟수에 비례하지 않는다.

- **결정 (사용자) — 부분 실패도 재시도한다. 건너뛰면 안 된다.**

  이 앱의 분석은 한 문단에 **네 파트**(번역·표현·구조·총평)를 따로 호출하므로
  **일부만 성공할 수 있다.** 그래서 "끝났나" 의 기준이 둘로 갈린다.

  ```
  건너뛰기   행이 있고 **failed_parts 가 비어 있을 때만**
  보여주기   모든 문단에 행이 있으면 (부분이라도)
  ```

  **행이 있는지로 건너뛰면 안 된다.** 세 파트만 성공한 행이 "이미 있음" 으로 읽혀
  총평이 영영 빈 문단이 **모든 회원에게 고정된다.** 회원 본인 분석은 지금 보는
  화면이라 부분이라도 보여주면 되지만, 공용은 **모두가 오래 볼 것**이라 기준이
  다르다.

  보여주기를 "완벽할 때" 로 잡지 않은 이유는 반대쪽이다 — **한 파트가 고집스럽게
  실패하면 그날 글감이 아예 안 나온다.** 부분이라도 내보내고 재시도가 뒤에서 채우면
  화면이 점점 나아진다.

  **삽입이 아니라 upsert 다.** `uq_analysis_paragraph_level` 이 걸려 있으므로
  재시도는 기존 행을 **갱신**해 빈 파트를 채운다.

  **끝없이 돌지는 않는다.** 작업의 대상은 "오늘 글감" 이므로 날이 바뀌면 어제 것의
  빈 파트는 더 안 건드린다. 상한을 따로 두지 않아도 **하루로 한계가 그어진다.**

- **쿨다운 5분의 성질** 하루 최대 288번. 가져오기 단계에서 실패하면 LLM 을 안
  부르므로 싸고, 분석 도중 실패는 위 5번 때문에 남은 문단만 다시 돈다.
  **5분은 설정값이 아니라 상수로 둔다** — 바꿀 이유가 생기면 그때 꺼낸다.

- **다음 걸음** `M13-T3`(문단 쪼개기) → `M13-T5`(미리 분석) → `M13-T6`(화면)을
  먼저 한다. 기사 하나를 손으로 넣어 두면 그 셋이 전부 돌아가고 **눈으로 확인할
  수 있는 것이 먼저 나온다.** 자동 선정은 그 위에 얹는다.

### M13-T5 · 미리 분석해 둔다
시작 2026-10-23 · 갱신 2026-10-23

- **전제** 쪼개기(`M13-T3`)와 표(`M13-T2`)가 끝났다. 남은 것은 **문단마다 분석을
  돌려 채우는 쪽**이고, 그 전에 **누구의 키로 도나**를 정해야 했다.

- **결정 (사용자) — 운영자 한 명의 키로 돈다.** 운영자는
  `qazcde.k@gmail.com`(김진웅). `users.is_operator` 열로 표시한다.

  **키를 새로 두지 않았다.** 운영자도 회원이라 `provider_keys` 에 이미 자기 키가
  있다. 설정 화면에서 등록한 그것을 그대로 쓴다 — 서버 환경변수에 LLM 키를 두면
  둘이 되어 어느 쪽이 쓰이는지 흐려지고, 암호화 보관 규약(`keys.py`)을 비켜 간다.

- **결정 (사용자) — cloud 전용이다** ([09 §3.8](../09-mode-matrix.md)).
  local 은 혼자 쓰므로 읽고 싶은 글을 그때 붙여 넣으면 된다. **표는 두 모드에 다
  만들어지고**(리비전이 하나다) 갈리는 것은 채우는 쪽이다.

  장치를 분기가 아니라 **데이터로** 걸었다 — local 부트스트랩 사용자에게 플래그를
  켜지 않으면 `find()` 가 `None` 을 주고 기능이 꺼진다. 모드 분기를 하나 더 두는
  쪽보다, 빼먹어도 local 에서 돌지 않는 쪽이 낫다.

- **플래그는 권한이다.** 그래서 **구글이 검증한 이메일**에서만 켜고
  (`email_verified`), **로그인할 때마다 다시 맞춘다** — 이메일이 바뀌면 꺼진다.
  한 번 켜고 두면 운영자가 바뀐 뒤에도 옛 계정이 공용 글감 키 권한을 든다.

- **이메일이 두 곳에 있지만 갈라지지 않는다.** 법적 문서의 운영 주체 정보가
  `frontend/src/legal/operator.ts` 에 이미 있다. 백엔드에 한 번 더 적고
  **두 값이 어긋나면 검사가 거부한다** — `M12-T5` 의 방침↔레지스트리 대조와 같은
  장치다. 마이그레이션에는 **세 번째 사본을 두지 않았다**(기존 행 백필 안 함) —
  거기엔 아무 장치도 닿지 않으므로 운영자가 바뀌는 날 조용히 틀린 채 남는다.

- **autogenerate 가 깨진 것을 냈다.** `is_operator` 를 `nullable=False` 인데
  기본값 없이 더해서, **기존 회원이 있는 표에서는 `column contains null values` 로
  거부당한다.** 직접 쳐서 확인했다. 빈 테스트 DB 에서는 통과하고 **배포본에서만
  깨지는** 종류다. `server_default=false` 로 고쳤다 (`07 §6.5` 3번이 적어 둔 경우).

- **제공자는 Gemini 로 고정했다** (`JOB_PROVIDER`). **운영자의 활성 선택을 따르지
  않는다** — 운영자가 설정 화면에서 제공자를 바꾸면 모든 회원이 보는 글감 품질이
  같이 흔들린다. 공용 글감은 회원 전역 설정과 따로 움직여야 한다.
  값도 맞는다: 기사 한 편 18문단 × 네 파트 = **72 호출**이고 무료 등급이 일 250 이라
  영·미 두 곳(144)까지 들어간다.

- **막힌 것** 운영자가 **Gemini 키를 아직 등록하지 않았다.** `provider_keys` 에
  행이 없으면 `decrypt` 가 빈 문자열을 주고 분석을 시작할 수 없다. 설정 화면에서
  등록해야 한다 — 대화로 받지 않는다.
