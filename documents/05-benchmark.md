# 05. 실측 기록 — 단일 호출 vs 파트 분할

환경: Qwen3.8-27B (UD-IQ4_XS), llama-server `-c 65536 -ngl 99 -fa on -np 1 --jinja`

## 1. 왜 쟀나

"분석을 파트별로 쪼개면 각 파트의 사고가 짧아지고 컨텍스트 압박도 줄지 않겠나"는 가설을
검증하기 위해서다. 단일/분할 × thinking on/off 네 조합을 같은 문단(5문장)으로 측정했다.

## 2. 결과

| 방식 | 총 시간 | 생성 토큰 | 사고 길이 |
|---|---|---|---|
| 단일 호출 / thinking OFF | **32.0초** | 908 | 0자 |
| 단일 호출 / thinking ON | 136.9초 | 3,058 | 5,706자 |
| 분할 4회 / thinking OFF | 43.1초 | — | 0자 |
| 분할 4회 / thinking ON | 411.0초 | — | 2개 파트가 한도에서 잘림 |

분할 / thinking OFF 파트별:

| 파트 | 시간 | 생성 토큰 |
|---|---|---|
| translation | 3.5초 | 98 |
| expressions | 19.6초 | 695 |
| structures | 14.8초 | 552 |
| overview | 5.2초 | 161 |

## 3. 가설은 틀렸다 — 쪼개면 사고가 오히려 길어진다

thinking ON 기준, 단일 호출은 전체 분석에 5,706자를 사고했는데
분할하면 **표현 풀이 하나에만 15,046자, 문장 구조에 14,163자**를 썼다.
둘 다 `max_tokens=4096` 에서 잘렸다(`finish=length`).

잘린 사고를 읽어 보면 같은 표현을 분류했다 뒤집기를 반복하고 있었다.
단일 호출에서는 스키마가 "번역 → 표현 → 구조 → 총평"이라는 **작업 순서를 강제**해
모델이 빨리 출력으로 넘어가는 반면, "표현만 뽑아라" 같은 열린 과제를 주면 멈출 지점을 못 찾는다.

**사고 길이는 파트 크기가 아니라 과제의 열린 정도에 비례한다.**
그래서 파트 프롬프트에도 개수 상한과 판별 기준을 구체적으로 못박았다
(`app/prompts/analysis.py` 의 `LEVEL_GUIDE`, 표현 유형 우선순위).

## 4. 컨텍스트 제한은 병목이 아니었다

가장 무거운 thinking ON 단일 호출조차 프롬프트 1천 + 생성 3천 = 약 4천 토큰으로,
65536 컨텍스트의 6%다. 컨텍스트가 모자란 적은 없었다.
걸리는 것은 언제나 **출력 예산(`max_tokens`)** 이고, 이는 쪼갠다고 줄지 않는다.

## 5. thinking 은 값에 비해 비싸다

단일 호출 기준 32초 → 137초로 **4.3배**인데 결과물 품질 차이는 눈에 띄지 않았다.
사전적 지식을 구조화하는 작업이라 추론 이득이 작은 것으로 보인다.
기본값은 `LLM_ENABLE_THINKING=false` 로 둔다.

## 6. 그래도 분할을 채택한 이유

속도만 보면 분할은 손해다(32초 → 43초). 그럼에도 채택한 것은 속도가 아닌 세 가지 때문이다.

1. **부분 실패 격리** — 전에는 한 섹션이 스키마를 어기면 분석 전체가 502였다.
   이제 그 파트만 재시도하고, 실패해도 나머지는 살아남는다.
2. **점진적 렌더링** — 번역이 3.5~7.5초에 먼저 뜨고 나머지가 차례로 채워진다.
   총 시간이 11초 늘어도 체감 대기는 오히려 짧다.
3. **작은 스키마** — GBNF 제약이 단순해져 모델이 형식을 지키기 쉽다.

실제 스트림 측정 (구어체 3문장, 프론트엔드 코드 경유):

```
  7.5s  translation 도착   (첫 화면 갱신)
 25.3s  expressions 도착
 40.6s  structures  도착
 46.1s  overview 도착 + done
```

## 7. 재현

측정 스크립트는 저장소에 두지 않았다. `documents/` 의 수치를 다시 확인하려면
`POST /api/analyze/stream` 을 `curl -N` 으로 받아 이벤트 도착 시각을 재면 된다.
