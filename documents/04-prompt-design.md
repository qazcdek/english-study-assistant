# 04. 프롬프트 설계

## 1. 원칙

1. **모델은 JSON만 만든다.** 마크다운 표, 구분선, 이모지, 인사말은 코드가 붙인다.
2. **필드마다 언어를 못 박는다.** `expression`은 영어 원문 그대로, 나머지 설명은 한국어.
3. **원문에 실제로 나온 표현만** 뽑는다. 사전에서 가져온 무관한 예시 금지.
4. **모르면 비운다.** 빈 배열이 환각보다 낫다 — 특히 `example` 필드.
5. 열거형 값은 스키마의 `enum`으로 강제해 표기 흔들림(`비격식` vs `비격식체`)을 막는다.
6. **enum 을 나열만 하면 모델이 한 값으로 쏠린다.** 각 값의 판별 기준과 예시를 주고
   우선순위대로 확인하게 해야 한다 (2.2 참고).
7. **필드 이름만으로는 부족하다.** 표의 칸마다 무엇이 들어가야 하는지 따로 명세해야
   사전 뜻 나열을 넘어선 설명이 나온다 (2.1, 2.4, 2.5 참고).
8. **하지 말아야 할 것은 정오 예시로 보여준다.** "어색하면 생략하라"는 지켜지지 않았지만,
   틀린 문장과 맞는 문장을 나란히 준 뒤에는 교정됐다.
9. **금지만으로 안 되면 데이터를 준다.** "단어 뜻 풀이를 하지 말라"는 지켜지지 않았다.
   앞 파트가 이미 뽑은 표현 목록을 실제로 넘겨 주자 중복이 사라졌다 (2.4 참고).
10. **무엇을 고를지를 정의한다.** 출력 형식만 정하면 모델이 아무거나 고른다.
   선정 기준을 주면 고르는 것 자체가 달라진다.

## 2. 파트별 프롬프트 구조

분석은 네 파트로 쪼개 각각 독립된 호출로 처리한다 (근거는 05-benchmark.md).
프롬프트는 `공통 서두 + 난이도 지침 + 파트별 과제` 세 조각을 조립해 만든다.

```
[공통 서두]
너는 한국인 영어 학습자를 돕는 영어 분석 전문가다.
주어진 영어 텍스트를 분석해, 지정된 JSON 스키마를 따르는 객체 하나만 출력한다.

공통 규칙:
- JSON 외의 텍스트, 인사말, 코드 펜스를 절대 덧붙이지 않는다.
- 영어 표현은 원문 그대로, 설명은 모두 한국어로 쓴다.
- 확실하지 않은 정보는 지어내지 말고, 항목을 빼거나 배열을 비운다.
- 정해진 개수 안에서 끝낸다. 후보를 끝없이 재검토하지 말고 판단이 서면 바로 출력한다.

[난이도 지침]  ← LEVEL_GUIDE[level]

[파트별 과제]  ← PART_SPECS[i].task
```

마지막 공통 규칙("끝없이 재검토하지 말라")은 실측에서 나온 것이다.
파트를 쪼개면 과제가 열려 있어 모델이 후보 분류를 반복하다 출력 한도에서 잘렸다.

각 파트의 JSON 은 항상 `{"<field>": ...}` 한 겹으로 감싼 형태다.
스키마 모양이 파트마다 일정해 파싱과 검증 코드가 단순해진다.

| 파트 | field | 응답 스키마 | 의존 |
|---|---|---|---|
| 자연스러운 번역 | `translation` | 문자열 | — |
| 표현 풀이 | `expressions` | 객체 배열 | — |
| 문장 구조 | `structures` | 객체 배열 | — |
| 총평 | `overview` | 객체 | `expressions` |

### 2.1 표현 풀이 — 칸별 명세

"표현을 뽑아라"라고만 하면 모델이 사전 뜻만 나열한다. 실제로 `weigh in` 의 설명이
"의견을 밝히다, 발언하다, 개입하다"로 끝나, 학습자가 이 문장에서 어떤 뜻으로 쓰였는지 알 수 없었다.
그래서 표의 **칸마다 무엇이 들어가야 하는지**를 프롬프트에 따로 명세했다.

| 칸 | 지침 요약 |
|---|---|
| `expression` | 원문에 실제로 등장한 표현만. **활용형이 아닌 사전 기본형** (`sums up` → `sum up`). 표현의 경계를 정확히 (`find its way across the pond` ✗ → `across the pond` ✓). 중복 금지 |
| `type` | 아래 2.2 의 우선순위 규칙 |
| `meaning` | **두 부분으로 쓴다.** 앞: 한국어 뜻(+유의어). 뒤: 원문에서 쓰인 뜻 / 비유의 유래 / 함께 쓰는 전치사·문형 / 격식 제약 중 해당하는 것을 한 문장. 사전 뜻 나열로 끝내지 않는다 |
| `example` | 5~12 단어의 단문. 원문 재사용 금지. **어순·전치사가 헷갈리면 아예 생략**한다 |

`example` 의 어순 규칙은 실측에서 나왔다. 구동사의 목적어 위치를 모델이 자주 틀려
`The critics threw at the movie many harsh reviews.` 같은 비문이 나왔다.
"목적어를 사이에 넣을 수 있는 구동사는 어순을 확신할 때만" 이라는 규칙과 정오 예시를 넣은 뒤
같은 문단에서 `Critics threw harsh words at the new director.` 로 교정됐다.

문체 통일(`~이다/~한다` 체)은 공통 규칙에 두었다. 파트마다 종결어미가 갈리는 문제가 있었다.

### 2.1.1 무엇을 고를 것인가 — 비합성성

Gemini 3.5 Flash-Lite 로 옮긴 뒤 드러난 문제다. 금융 칼럼 한 문단에서 뽑은 다섯 개가
`financial advisor` · `emotional support` · `sudden rally` · `panic selling` · `market volatility`
로, **전부 형용사+명사 / 명사+명사 의 투명한 복합어**였다. 낱말 뜻을 합치면 의미가 그대로 나오는,
중급 학습자가 굳이 배울 필요 없는 것들이다. 게다가 `key_expressions` 로 꼽힌 셋이
하필 가장 투명한 것들이었다.

같은 문단에서 정작 빠진 것들:

| 빠진 표현 | 학습 가치 |
|---|---|
| `indices` | `index` 의 불규칙 복수형. 한국인 학습자의 전형적 함정 |
| `a blend of A and B` | 비유적 표현 |
| `grow wealth` | `grow` 의 타동사 용법 |
| `lead to` | phrasal verb |

원인은 프롬프트가 "학습 가치가 낮은 기초 어휘는 제외"라고만 적은 데 있었다.
모델이 이를 **"기초 단어가 아니면 통과"** 로 해석한다. `financial advisor` 는 기초 단어가 아니다.

그래서 선정 기준을 **낱말 뜻을 합쳐서 의미를 짐작할 수 있는가(비합성성)** 로 못박았다.

- **우선할 것** — 낱말 합과 뜻이 다른 표현, 그 글에서 만들어 쓴 조어,
  불규칙 변화형, 함께 쓰는 전치사·문형이 정해진 표현
- **뒤로 미룰 것** — 투명한 복합어, 기초 어휘

정오 예시를 함께 줬다. `financial advisor`·`emotional support`·`market volatility` 를
"뒤로 미룰 것"의 예로 명시했다.

### 2.1.2 개수는 프롬프트가 아니라 스키마로 강제한다

프롬프트에 "3~8개" 라고 적어도 모델은 하한만 맞추고 만다. Flash-Lite 는 4~5개에서 멈췄다.
JSON 스키마의 `minItems`/`maxItems` 는 llama-server 든 Gemini 든 토큰 단계에서 강제되므로
문구보다 확실하다.

난이도별로 다르게 줘야 하므로 `PartSpec.schema_for(level)` 이 요청마다 개수를 얹는다.

| level | minItems | maxItems |
|---|---|---|
| beginner | 3 | 5 |
| intermediate | 5 | 8 |
| advanced | 5 | 8 |

**상급이라고 개수를 늘리면 안 된다.** 처음에는 상급을 7~10개로 뒀는데, 짧은 글에서 하한을
채우려고 모델이 좋은 다어절 표현을 **낱개 단어로 쪼갰다.**

```
중급  a blend of             →  상급  blend
중급  share this perspective →  상급  perspective
중급  market volatility      →  상급  volatility
```

상급 결과가 중급보다 오히려 쉬워지는 역전이 일어났다.
난이도는 **설명의 깊이**를 바꾸는 것이지 개수나 난도를 바꾸는 것이 아니다.
그래서 중급과 상급의 개수를 같게 두고, `LEVEL_GUIDE` 의 상급 항목에
"표현을 더 많이 뽑거나 쉬운 낱말까지 끌어오지 않는다"를 명시했다.
`expression` 칸 명세에도 "개수를 채우려고 다어절 표현을 낱개로 쪼개지 않는다"를 넣었다.

`key_expressions` 도 `minItems: 1, maxItems: 3` 으로 묶었다.
"특히 챙길 것"이라는 선별의 뜻이 살려면 목록 전체를 옮겨 적으면 안 된다.

### 2.1.3 적용 효과 (같은 금융 칼럼 문단, Gemini 3.5 Flash-Lite)

| | 수정 전 | 수정 후 |
|---|---|---|
| 개수 | 5개 | **7개** |
| 유형 분포 | 연어 3 · 전문 용어 2 | 연어 · 고급 어휘 · 관용구 · 전문 용어 · Phrasal Verb · 문법 포인트 |
| `indices` | 누락 | **문법 포인트로 포착**, "index의 불규칙 복수형" |
| `a blend of` / `grow`(타동사) / `lead to` | 누락 | 모두 포착 |
| 투명한 복합어 | 5개 전부 | 빠짐 |
| `key_expressions` | 3개 (가장 투명한 것들) | 2개 (비합성적인 것들) |

### 2.2 표현 유형 분류 기준

`type` 의 enum 값만 주면 모델이 대부분을 `고급 어휘`로 몰아넣는다.
실제로 Qwen3.8-27B 에서 `across the pond`(관용구), `sum up`(Phrasal Verb), `cope with`(연어)이
전부 `고급 어휘`로 분류됐다. 그래서 프롬프트에 **위에서부터 확인하는 우선순위 규칙**을 넣었다.

| 순위 | 유형 | 판별 기준 | 예 |
|---|---|---|---|
| 1 | Phrasal Verb | 동사 + 부사/전치사이고 낱말 뜻의 합과 의미가 다름 | sum up, throw at |
| 2 | 관용구 | 굳어진 비유 표현, 직역하면 뜻이 안 통함 | across the pond |
| 3 | 연어(Collocation) | 습관적으로 함께 쓰는 자연스러운 단어 짝 | cope with |
| 4 | 구어 표현 | 대화·비격식 글에서 주로 씀 | |
| 5 | 전문 용어 | 특정 분야의 용어 | |
| 6 | 문법 포인트 | 뜻이 아니라 문법 형태 자체가 학습 대상 | -prone 복합 형용사 |
| 7 | 고급 어휘 | 위 어디에도 해당하지 않는 수준 높은 단일 단어 | trumpet |

규칙 추가 후 같은 문단에서 위 세 표현이 모두 올바르게 분류됐다.

### 2.3 칸별 명세의 효과

같은 문단, 같은 모델에서 `across the pond` 의 설명 변화:

| | 설명 |
|---|---|
| 명세 전 | (비격식) 대서양을 건너 — 주로 영국과 미국 사이를 가리킬 때 쓴다 |
| 명세 후 | 대서양 건너편으로, 영국과 미국 사이를 오가는 것을 의미한다. **대서양을 '연못(pond)'에 빗댄 친근한 비유 표현이다** |

`throw at` 도 명세 전에는 원문 활용형 `thrown at` 으로 잡히던 것이 기본형으로 교정됐다.

### 2.4 문장 구조 — 칸별 명세

명세 전 출력에서 나온 문제:

| 문제 | 사례 |
|---|---|
| 어휘 설명이 새어 들어옴 | `wanna`, `bail on`, `flake out`, `I get it` 이 구조 항목으로. 그중 둘은 표현 풀이 표와 **그대로 중복** |
| fragment 경계가 제멋대로 | 5자(`wanna`)~124자(문장 전체). 문장 전체를 인용하고 설명은 그 안의 분사구문 하나에 대한 것 |
| 범위 중복 | `Once the migration has been applied` 와 `has been applied` 가 별도 항목으로 |
| 형태 명명에서 끝남 | "미래 시제 수동태 구조이다" 로 시작하는 수동태 일반론. 이 문장에서 왜 수동태인지는 없음 |
| 독해에 무의미한 사실 | "that은 관계대명사절 안에서 주어가 된다" |
| 용어 오류 | "동명사구(suggesting)가 현재분사구문으로 기능하여" |
| 막연한 상찬 | "문장의 긴장감을 줄이고 자연스럽게 정보를 연결하는 고급 문법 구조입니다" |

가장 좋았던 항목은 `Had she known` 해설이었다. 차이는 **쉬운 말로 바꿔 쓴 등가 표현**
(`If she had known` 과 같다)이 있다는 점이었다. 이것을 명세의 축으로 삼았다.

**교육학적 근거.** VanPatten 의 입력 처리 원리상 학습자는 어휘 단서를 먼저 처리하고
문법 표지는 건너뛴다. 따라서 어휘만으로 뜻이 드러나는 구조는 설명 가치가 낮고,
어휘를 다 알아도 뜻이 안 잡히는 구조가 가치가 높다 — 이것을 **선정 기준**으로 삼았다.
한국어는 수식어가 명사 앞에 오므로 긴 후치 수식구가 한국인 학습자의 전형적 오독 지점이고,
Schmidt 의 noticing 관점에서 형태와 기능을 함께 짚어야 하므로 해설을 3단으로 고정했다.

| 칸 | 지침 요약 |
|---|---|
| 선정 기준 | 단어 뜻을 다 알아도 구조가 안 잡히는 지점만. 도치·생략, 형식주어, 긴 후치 수식, 숨은 주어, 가정법, 행위자를 감춘 수동태, 부정어 범위 |
| 제외 | 단어·숙어 뜻(표현 풀이 담당), 독해가 달라지지 않는 문법 사실, 같은 구조의 범위만 바꾼 중복 |
| `fragment` | 구조가 드러나는 **최소 범위**만 원문 그대로. 문장 전체 금지. 항목 간 범위 겹침 금지 |
| `name` | 구조 이름. 표준 문법 용어로 짧게 |
| `role` | **이 문장에서** 하는 일. 문법 일반론·평가어 금지 |
| `rewrite` | 같은 뜻으로 구조를 풀어낸 **영어** 문장. 어려우면 빈 문자열 |
| `pitfall` | 한국어 화자가 놓치기 쉬운 지점. 없으면 빈 문자열 |

**3단 구성은 한 필드에 몰아넣어서는 지켜지지 않았다.** "①②③을 순서대로 쓰라"고 지시해도
모델이 ③을 "~하는 데 도움을 준다" 같은 일반론으로 때웠다. 필드를 나눠 `required` 로 묶으니
각각을 반드시 채워야 해서 빠뜨릴 수 없게 됐다.

`rewrite` 를 **영어 문장**으로 못박은 것이 핵심이다. "쉬운 말로 바꿔 쓰기"라고만 하면
한국어 번역을 쓴다. 번역은 이미 번역 파트가 한다.

**어휘 중복은 프롬프트 금지만으로 잡히지 않았다.** "단어 뜻 풀이는 하지 않는다"가 이미 있는데도
`wanna`, `flake out` 이 들어왔다. 구조 파트가 표현 파트 **다음에** 실행된다는 점을 이용해,
앞서 뽑힌 표현 목록을 프롬프트에 실어 보내고 "이 어구 자체를 fragment 로 삼지 말라"고 지시했다.
그 뒤 같은 문장에서 `left holding the bag` → `we are gonna be left holding the bag` 으로,
즉 더 큰 구조의 일부로 다루게 바뀌었다.

### 2.5 총평 — 칸별 명세

명세 전 출력에서 나온 문제:

| 문제 | 사례 |
|---|---|
| `domain` 이 장르가 아니라 화행 | "일상적 갈등 상황에서의 구두 설득", "일상적 갈등 해결" |
| `domain` 이 실행마다 흔들림 | 같은 텍스트가 "친구 간 일상 대화" ↔ "일상적 갈등 해결" |
| 근거 없는 추측 | 환상 요소가 없는 문장에 "가상 서사·**환상** 문학" |
| `tone` 이 `style` 을 되풀이 | "공감하면서도 불만을 직설적으로 표현하는 **구어체**" |
| `formality`/`style` 판정 흔들림 | 같은 시사 문단이 (격식, 문어체) ↔ (중립, 구어체) |
| `comment` 가 작품 해설로 흐름 | "운명과 심리적 결정을 연결하는 핵심 축", "독자로 하여금 긴장감을 고조시킨다" |
| 수용/표현 구분 없음 | 모든 코멘트가 "활용할 수 있다" 로 끝남. `wanna`/`gonna` 까지 |

**교육학적 근거.** Halliday 의 register 삼분(field·tenor·mode)이 네 필드에 거의 그대로 대응한다
— `domain`=field, `tone`=tenor, `style`=mode, `formality`=tenor 의 일부.
각 칸에 이 정의를 못박으면 `tone` 이 `style` 을 되풀이하는 문제가 구조적으로 해소된다.
또 어휘 지식에는 수용(알아보기)과 표현(직접 쓰기) 층위가 나뉘는데, 기존 코멘트는 전부
표현 층위로 뭉뚱그렸다. 비격식 표현을 격식 글에 잘못 쓰는 것은 한국인 학습자의 흔한 실수라
"이건 알아만 두고 이건 써라"의 구분을 코멘트 필수 항목으로 넣었다.

| 칸 | 지침 요약 |
|---|---|
| `domain` | **어디에 실릴 법한 글인지** (경제 신문 칼럼, 임상 연구 논문, 개발자용 기술 문서, 친구 간 메신저 대화). 주제나 목적이 아님. 근거 없는 장르 추측 금지 |
| `tone` | **글쓴이가 독자를 대하는 태도** (단정적인, 조심스럽게 유보하는, 가볍게 비꼬는). "격식/비격식/문어체/구어체" 낱말 사용 금지 |
| `formality`/`style` | 인상이 아니라 **본문의 표지**로 판정. 축약형·속어·말 거는 you ↔ 수동태·명사화·긴 후치 수식·일인칭 부재 |
| `key_expressions` | 받은 표현 목록에 있는 것만, 1~3개 |
| `comment` | ①왜 핵심인지 ②**직접 써도 되는 것과 뜻만 알아둘 것 구분**, 격식 글에서 피할 표현은 반드시 명시 ③써먹을 상황. 3~4문장 이내. 작품 해설 금지 |

### 2.6 명세 적용 효과

| | 명세 전 | 명세 후 |

쉽게   If she had known what awaited her at the end of that corridor
주의   if가 생략된 것을 알아채지 못해 평서문이나 의문문으로 오독하기 쉽다.

### 2.7 작문 연습 채점 프롬프트

분석 4파트와 별개로, 작문 연습 채점 프롬프트가 `app/prompts/practice.py` 에 있다.
같은 원칙(칸별 명세, enum 강제, 한국어 문체 통일)을 따르되 교정 피드백 특유의 제약이 더 있다 —
모범 답안을 유일한 정답으로 취급하지 않기, 지적을 최대 2개로 제한하기, 잘한 점 먼저 짚기.
근거와 실측은 [06-practice.md](06-practice.md) 참고.

## 3. JSON 스키마 (llama-server `response_format` 으로 전달)

`backend/app/prompts/analysis.py` 의 `PART_SPECS[i].schema` 가 단일 원본(single source of truth)이며,
`backend/app/schemas.py` 의 파트 모델(`TranslationPart`, `ExpressionsPart`, `StructuresPart`,
`OverviewPart`)과 1:1로 대응한다. 한쪽을 바꾸면 다른 쪽도 바꾼다.

llama-server 는 GBNF 문법으로 변환해 토큰 단계에서 스키마를 강제하므로,
`additionalProperties: false` 와 `required` 를 빠짐없이 지정하는 것이 중요하다.

## 4. 난이도(level)별 조정

| level | 조정 |
|---|---|
| `beginner` | 문법 용어를 최소화하고 풀어서 설명. 구문 해설 2개 이하 |
| `intermediate` | 기본값. 일반적인 문법 용어 사용 |
| `advanced` | **설명을 깊게** — 뉘앙스·어원·유사 표현 비교·쓰면 어색해지는 자리까지 |

난이도는 **설명의 깊이만** 바꾼다. 표현 개수와 선정 기준은 초급을 제외하면 같다.
이유는 2.1.2 참고.

## 5. 실패 대응

재시도와 실패 처리는 **파트 단위**로 이루어진다.

1. 응답이 JSON 파싱 또는 Pydantic 검증에 실패
2. 코드 펜스(` ```json `) 제거, 첫 `{` ~ 마지막 `}` 만 잘라내 재파싱 시도
3. 그래도 실패하면 **temperature 0.0 + "JSON만 출력하라" 강조 메시지**로 그 파트만 1회 재호출
4. 최종 실패 시 그 파트에 대해 `part_error` 이벤트를 내보내고 **다음 파트로 넘어간다**
5. 연결 불가·타임아웃이면 남은 파트도 소용없으므로 즉시 중단
6. 모든 파트가 실패한 경우에만 `/api/analyze` 가 502 `llm_bad_output` 을 돌려준다

## 6. 모델 선택 메모

작은 모델일수록 한국어 설명 품질이 급격히 떨어진다. 한국어 출력이 핵심이므로
**한국어 성능이 확인된 7B 이상 instruct 모델**을 권장한다.
JSON 스키마 강제는 llama-server 가 처리하므로 function calling 지원 여부는 중요하지 않다.

### 6.1 검증 환경

Qwen3.8-27B (UD-IQ4_XS, `-c 65536 -ngl 99 -fa on --jinja`) 로 확인:

- `response_format: json_schema` 정상 동작. enum 값도 그대로 지켜진다.
- **thinking 은 꺼야 한다.** 켜면 사고가 `max_tokens` 를 전부 소진한다 (02-architecture.md 8절).
- 5문장 문단 전체 분석에 **약 29~35초**, 재시도 없이 1회 성공.

## 7. 총평(overview) 재정의

초안에는 `frequency`(사용 빈도) 열거값이 있었으나 **제거했다.** 같은 문단을 두고 모델이
`자주`와 `매우 드묾`을 오갔고, 판단 대상이 문단 전체인지 개별 표현인지도 정의되지 않았다.
열거값으로 강제해도 판단 기준 자체가 모호하면 일관성이 생기지 않는다.

대신 총평을 **"어떤 분야에서 어떤 톤으로 쓰인 글이고, 어떤 표현이 중요한가"** 로 재정의했다.

| 필드 | 형태 | 프롬프트 지침 |
|---|---|---|
| `domain` | 자유 서술 | 어떤 분야의 글인지 짧은 구로 |
| `tone` | 자유 서술 | 글쓴이의 태도·어조. formality/style 과 겹치는 말을 반복하지 말 것 |
| `formality` | 열거값 | 기존 유지 |
| `style` | 열거값 | 기존 유지 |
| `key_expressions` | 배열 | expressions 중 1~3개. `expression` 값과 글자 그대로 일치할 것 |
| `comment` | 자유 서술 | 왜 중요하고 어디에 써먹는지 두세 문장 |

`key_expressions` 를 표의 `expression` 과 문자열로 일치시키게 한 덕분에,
프론트에서 해당 행에 ★ 를 붙여 총평과 표를 연결할 수 있다.
실측에서 시사 문단·구어 문장 모두 불일치 없이 정확히 일치했다.

## 8. 남은 개선 여지

- ~~`tone` 이 `style` 의 값을 되풀이한다~~ → 2.5 에서 낱말 사용 자체를 금지해 해결.
- 구조 해설에서 모델이 문법 용어를 헐겁게 쓴다. first conditional 을 "제1종 가정법",
  단순 조건의 결과절을 "제2종 가정법" 으로 부르는 등. 명세로 교정되지 않는 모델 지식의 한계다.
- 구조 해설이 "이 구조는 ~이다" 로 매번 시작한다. 읽기에 단조롭다.
- `example` 의 비문 문제는 어순 규칙 + 정오 예시로 잡혔다(2.1). 다만 표본이 두 문단이라,
  다른 구동사에서 다시 나타나는지 지켜볼 필요가 있다.
- `left holding the bag` 처럼 관용구의 기본형을 무엇으로 볼지 애매한 경우가 남아 있다
  (`be left holding the bag` / `leave someone holding the bag`).
- `key_expressions` 가 표에 없는 표현을 가리켜도 지금은 그대로 표시한다.
  실측에서는 발생하지 않았고, 조용히 버리는 것보다 낫다고 판단했다.
