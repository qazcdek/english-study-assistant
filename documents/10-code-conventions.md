# 10. 코드 규약

> **층** 규약 · **상태** 유효 · **강제** `backend/tests/`, `ruff`
> **읽어야 할 때** 코드를 쓰기 전에. [CLAUDE.md](../CLAUDE.md) 6절의 원칙을 구체적으로 풀어 둔 곳
> **위** [문서 지도](00-index.md) · **함께** [아키텍처](02-architecture.md) · [프롬프트 설계](04-prompt-design.md) · [모드별 차이](09-mode-matrix.md)

CLAUDE.md 에는 **원칙**만 둔다. 값·파일명·프로바이더 차이처럼 **바뀌는 것**은 여기 적는다.

## 1. 언어와 문체

주석과 문서는 한국어, 설명체(`~이다` / `~한다`)로 쓴다.
주석은 **무엇을 하는지가 아니라 왜 그런지**를 적는다. 코드가 이미 말하는 것을 되풀이하지 않는다.

```python
# 나쁨: is_cloud 면 사용량을 센다          ← 코드가 이미 말한다
# 좋음: 회원 각자의 Gemini 한도를 쓰는 cloud 에서만 센다 (09-mode-matrix.md 3.3)
```

## 2. LLM 에 거는 제약은 스키마로

부탁하면 안 지켜지고, 스키마로 요구하면 지켜진다. 개수·필수 필드는 전부 `response_format` 쪽에 둔다.

**프로바이더마다 지원 범위가 다르다.** 실측은 [05-benchmark.md](05-benchmark.md).

| 제약 | Gemini | llama-server |
|---|---|---|
| `minItems` / `maxItems` | 지킴 | 지킴 |
| `pattern` | 지킴 | **폭주하거나 무시한다** |
| `maxLength` | 지킴 | **낱말 중간에서 잘라 버린다** |
| `minLength` | 지킴 | **계속 생성해 `max_tokens` 를 넘긴다** |

양쪽에서 도는 스키마에는 아래 셋을 쓰지 않는다. 길이나 모양을 맞춰야 하면
프롬프트의 정오 예시로 유도하고, 코드(`app/services/refine.py`)에서 다듬는다.

## 3. 모드별 값은 한 곳에서만 갈린다

`app/config.py` 바깥에 모드 분기를 흩뿌리지 않는다. 갈리는 항목 전체는
[09-mode-matrix.md](09-mode-matrix.md) 가 들고 있고, `tests/test_mode_matrix.py` 가 그 표를 고정한다.

테스트를 어디에 두는지도 규약이다.

- **두 모드 공통 기능** → `tests/test_both_modes.py` 의 `both_modes` 픽스처. 모드마다 한 번씩 돈다.
- **모드 전용 동작** → `tests/test_cloud.py`

공통 기능을 한쪽에만 두면 다른 쪽이 깨져도 안 잡힌다. 자세한 것은 [09 6절](09-mode-matrix.md).

## 4. 저장된 결과의 형식이 바뀔 때

프롬프트를 손볼 때마다 결과 스키마가 바뀌는데, DB 에는 그때그때의 형식으로 남아 있다.

**Pydantic 모델을 느슨하게 만들어 해결하지 않는다.** 같은 모델이 LLM 응답 검증에도 쓰이므로,
모델이 필드를 빠뜨려도 조용히 통과하게 된다. 대신:

1. 모델은 엄격하게 둔다.
2. `app/services/records.py` 에서 **읽을 때만** 형식을 올린다.
3. 스키마를 바꿀 때마다 `RESULT_VERSION` 을 올리고 변환 규칙을 추가한다.

근거와 실제 사고 기록은 [07 §8.1](07-web-deployment.md).

## 5. 비밀값

- `backend/.env*` 는 gitignore 되어 있다. 값을 커밋이나 대화에 남기지 않는다.
- 회원의 Gemini 키는 Fernet 으로 암호화해 저장한다. 평문은 서버 밖으로 나가지 않고,
  돌려주는 것은 마지막 네 자리뿐이다.
- **`ENCRYPTION_KEY` 는 교체하지 않는다.** 바꾸면 이미 등록된 회원 키를 복호화할 수 없다.

## 6. 검증의 한계

- **hover 같은 포인터 동작은 headless 브라우저로 확인되지 않는다.**
  headless Chrome 은 `hover: hover` 와 `pointer: fine` 을 false 로 보고해서,
  멀쩡한 기능이 깨진 것처럼 보인다. 직접 띄워 본다.
- **LLM 응답 품질은 테스트로 고정되지 않는다.** 프롬프트를 바꾸면 실제로 돌려 보고
  달라진 점을 [05-benchmark.md](05-benchmark.md) 나 해당 설계 문서에 남긴다.

## 7. 근거 문서는 주소로 적는다

왜 그런지를 주석에 전부 옮겨 적을 수는 없다. 판단이 담긴 문서를 **가리킨다.**
그 포인터는 한 가지 형태로만 적는다.

```
09-mode-matrix.md          문서 전체를 가리킬 때
09-mode-matrix.md §3.1     절을 가리킬 때
```

- **`documents/` 접두사를 붙이지 않는다.** 파일명이 이미 유일하다.
- **`3.1절` 이나 그냥 `3.1` 로 적지 않는다.** `§` 가 있어야 기계가 절 번호인 줄 안다.
- 문장 안에 괄호로 넣어도 된다 — `(09-mode-matrix.md §3.1)`. 형태만 지키면 된다.

**형태가 하나여야 검사할 수 있다.** 문서 번호는 뜻이 아니라 주소이므로
([11 §3.3](11-docs-architecture.md)), 파일명이 바뀌거나 절 번호가 밀리면 주석이
조용히 엉뚱한 곳을 가리킨다. `backend/tests/test_doc_references.py` 가
**모든 주소를 실제로 찾아가 본다** — 없는 문서, 없는 절, 어긋난 표기 전부 실패한다.

**문서끼리의 주소도 본다.** 문서 사이에서는 절 번호를 링크 글자 안에 넣는다 —
`[07 §6.5](07-web-deployment.md)`. 한동안 코드→문서만 보고 있었고, 그래서 참조받는
절의 번호를 바꿔도 통과했다. 켜자마자 `04 §1.4` 라는 **없는 절을 가리키는 주소**가
하나 나왔다 (M11-T2).

반대 방향도 짝이 맞아야 한다. 문서 머리말의 `강제` 가 테스트를 가리키면,
**그 테스트도 문서 이름을 알고 있어야 한다.** 한쪽만 아는 포인터는 끊긴 것과 같다.

## 8. 포인터는 한 방향만 손으로 적는다

7절은 **코드 → 문서** 방향이다. 사람이 산문 안에 적는다. 반대 방향 —
*어떤 문서가 이 코드를 근거로 들고 있는가* — 는 **문서에 적고 코드에는 생성한다.**

문서 쪽 (손으로 적는 유일한 쪽):

```
`→ backend/app/config.py`                                   모듈
`→ backend/app/config.py::Settings`                         클래스
`→ backend/app/config.py::Settings.max_input_chars`         메서드
`→ backend/app/routers/analyze.py::_check_length`           함수
```

코드 쪽 (`./dev.sh ptr --write` 가 씀):

```python
def _check_length(request: AnalyzeRequest) -> None:
    """모드별 입력 상한. 스키마의 절대 상한보다 좁다.

    [문서] 09-mode-matrix.md §3.1
    """
```

- **`[문서]` 줄은 도구가 소유한다.** 손으로 고치지 않는다. 문서가 가리키기를 그만두면
  따라 사라지고, docstring 이 없으면 만들어 붙인다.
- **줄 번호를 쓰지 않는다.** 주소는 AST 로 푼다. 코드를 옮기거나 import 를 더해도
  포인터는 그대로고, **이름이 바뀌면 실패한다** — 가리키던 것이 실제로 없어졌으니까.
- **대상은 모듈·클래스·함수다.** 변수는 마커를 붙일 자리가 없으므로 감싸는 쪽을 가리킨다.
- 생성 마커와 **같은 곳**을 가리키는 산문 인용이 7절에 있으면 산문 쪽을 지운다.

일하는 순서는 하나다 — **문서를 고치고 `./dev.sh ptr --write`.** CI 가
`./dev.sh ptr` 로 생성물이 문서와 맞는지 보고, 어긋나면 실패한다.

이런 검사·생성 도구를 **어떻게 만들고 어디에 등록하는지**는
[12 도구 규약](12-tooling.md).

## 9. 화면이 너비에 따라 갈릴 때

표현 풀이는 **넓은 화면에서 표, 좁은 화면에서 카드**로 그린다. 칸이 다섯이면 폰에서
어떤 열 너비를 줘도 읽히지 않고, 가로로 밀게 하면 공부하다 손이 멈춘다.

### 9.1 배치만 갈리고 내용은 한 벌이다

두 배치가 각자 조각을 들면 **한쪽만 고쳐져 갈라진다.** 표에만 유형 배지를 더하고
카드에는 안 더하는 식이다. 그래서 내용 조각(표현 · 유형 배지 · 핵심 배지 · 의미 ·
예문 자리 · 별)을 작은 컴포넌트로 뽑아 **두 배치가 같은 것을 쓴다.**

검사가 같은 물음을 **두 너비에서 모두** 던진다 — 별이 토글되는지, 확인 상자가 뜨는지,
핵심 배지가 붙는지, 연습을 열 수 있는지. 한쪽만 고치면 깨진다.

### 9.2 두 벌을 심고 CSS 로 숨기지 않는다

`sm:hidden` 과 `hidden sm:block` 으로 두 벌을 다 심으면 화면에는 하나만 보이지만
**DOM 에는 둘이 있다.** 그러면 같은 글이 두 번 읽히고(스크린 리더), 검사도 "그 글자가
하나뿐인가" 를 물을 수 없다. 실제로 그 꼴을 흉내 내 보니 **검사 27개가 깨졌다.**

분기는 JS 로 가져온다 — `frontend/src/lib/useIsWide.ts` 의 `useIsWide()`.
그러면 DOM 에 한 벌만 남는다. (**화살표 포인터를 쓰지 않았다** — `./dev.sh ptr` 은
`.py` 만 푼다. 프론트엔드는 코드가 문서를 가리키는 방향으로 잇는다, 7절.)

**너비 값은 두 곳에 있다.** CSS 는 `sm:` 접두사로만 쓰고 JS 는 값을 알아야 한다.
`useIsWide.ts` 의 `WIDE` 가 JS 쪽 유일한 원본이고, 바꿀 때 `sm` 을 함께 본다.

### 9.3 자동 검증이 닿지 않는 곳

검사는 **내용이 같은지**를 본다. **픽셀이 맞는지는 못 본다** — jsdom 에는 레이아웃이
없다. 여백이 좁은지, 글이 잘리는지, 다크 모드에서 대비가 모자란지는 사람이 본다
(6절과 같은 경계다).
