# 11. 문서 아키텍처

> **층** 메타 · **상태** 유효
> **읽어야 할 때** 문서 구조를 바꾸려 할 때. **이 방식을 다른 프로젝트로 옮길 때**
> **위** [문서 지도](00-index.md) · **함께** [CLAUDE.md](../CLAUDE.md) · [00 문서 지도](00-index.md)

코드에 아키텍처가 필요하듯 문서에도 필요하다. 이 문서는 **왜 이렇게 설계했는가**를 적는다.
*어디에 무엇이 있는지*는 [00 문서 지도](00-index.md)가, *무엇을 지켜야 하는지*는
[CLAUDE.md](../CLAUDE.md)가 든다. 셋이 겹치지 않게 나눈 것 자체가 이 설계의 일부다.

## 1. 문서는 왜 안 읽히는가

"문서를 잘 쓰자" 로는 아무것도 해결되지 않는다. 실패는 네 가지 모양으로 온다.
**뒤로 갈수록 흔하고, 뒤로 갈수록 눈에 안 띈다.**

| 실패 | 증상 | 이 프로젝트에서의 실측 |
|---|---|---|
| **고아** | 아무도 가리키지 않아 존재를 모른다 | 0건. 색인이 있어서 |
| **막다른 문서** | 들어가면 되돌아 나올 길이 없다 | **9개 중 5개** (05·06·07·08·09) |
| **안 펴보는 문서** | 있는 줄 알면서 안 펴고 고친다 | 측정 불가. **가장 흔하다** |
| **썩은 문서** | 코드는 바뀌었는데 문서는 그대로 | H-011, H-014 |

고아만 막는 설계는 네 중 하나만 막는다. 색인 하나 두고 끝내면 나머지 셋이 남는다.

**썩음은 특히 빠르다.** 로컬과 웹을 한 코드베이스로 합친 뒤 **커밋 하나 만에**
주석 세 곳이 문서와 어긋났고(H-011), 브랜치를 합친 뒤 문서 네 곳이
`local`/`main` **브랜치**로 설명한 채 남아 있었다(H-014).
같은 커밋 안에서 한 곳만 제대로 고쳐졌다 — 사람의 주의력이 문제가 아니라,
**주의력에 기대는 설계**가 문제다.

## 2. 네 가지 원리

### 2.1 색인은 하나뿐이다

둘이 되면 갈라진다. 추측이 아니라 실제로 그랬다 — README 에 14개, 00-index 에 13개가
적혀 있었다. 어느 쪽이 맞는지는 아무도 모른다.

그래서 README 는 **설치·실행 안내**로 역할을 좁히고, 문서 입구는 색인 하나로 둔다.

### 2.2 모든 문서가 되돌아 나간다

각 문서 머리말의 `위` 가 색인을 가리킨다. 이 한 칸이 **고아와 막다른 문서를 동시에,
구조적으로** 없앤다 — 색인에서 내려가는 길과 문서에서 올라오는 길이 모두 생기기 때문이다.

`함께` 는 옆으로 가는 길이다. 색인까지 돌아가지 않고 관련 문서로 건너뛴다.

> 적용 전후: 나가는 링크가 0인 문서 5개 → 0개. 색인으로 들어오는 링크 2개 → 15개.

### 2.3 "읽어야 할 때" 를 문서 자신이 든다

**이것이 이 설계에서 가장 중요한 칸이다.** 나머지 셋은 문서를 *찾게* 해 주지만,
이 칸만이 문서를 *펴게* 만든다.

색인에만 적으면 색인을 거쳐 온 사람에게만 닿는다. 그런데 실제로는 코드 주석의 링크를 타거나,
검색으로 바로 들어오는 경우가 더 많다. 그 사람에게는 아무 신호가 없다.

그래서 트리거는 **문서 자신이** 들고 있어야 한다.

```
> **읽어야 할 때** 모드에 따라 갈리는 것을 바꿀 때 — 코드를 고치기 전에
```

같은 정보를 **작업 → 문서** 방향으로도 한 번 더 적는다
([CLAUDE.md 4절](../CLAUDE.md)). 문서를 열기 전에 이미 작업을 시작한 사람을 위해서다.
두 방향 모두에서 닿아야 한다.

### 2.4 상태로 수명을 선언한다

문서마다 **유효 · 기록 · 대체됨** 중 하나를 머리말에 적는다.

- **유효** — 지금 코드가 이대로다. 코드가 바뀌면 같이 바꾼다.
- **기록** — 그때의 측정이거나 판단이다. **지금 사실에 맞춰 고치지 않는다.**
- **대체됨** — 다른 문서로 넘어갔다. 넘어간 곳을 적는다.

이게 없으면 두 가지 실수가 번갈아 난다. 살아 있는 문서를 안 고쳐 썩히거나,
**기록 문서를 현재에 맞춰 고쳐 그때의 판단을 지워 버리거나.**

실제 사례: `08-level-design.md` 에는 지금도 "`local` 브랜치는 llama-server 를 쓰므로"
라는 낡은 서술이 남아 있다. **기록 층이라 일부러 두었다.** 그 문장이 틀렸다고 고치면
"그때는 브랜치가 둘이었고 그래서 `pattern` 을 못 썼다" 는 판단 근거가 사라진다.

## 3. 층 — 번호가 아니라 머리말로

문서 번호(01~11)는 **시간 순**이라 성격을 알려주지 않는다. `09` 는 테스트가 강제하는
규약이고 `08` 은 끝난 기획안인데, 번호만 보면 같은 무게로 보인다.

그렇다고 번호를 다시 매기면 안 된다. **번호는 뜻이 아니라 주소다** —
코드 주석 아홉 곳이 `09-mode-matrix.md 3.1` 같은 형태로 가리키고 있다.
층이 바뀌어도 주소는 그대로 두고, 성격은 머리말의 `층` 으로만 표시한다.

| 층 | 무엇인가 |
|---|---|
| 메타 | 문서 체계 자신에 관한 것 |
| 제품 | 무엇을 왜 만드는가 |
| 설계 | 어떻게 만들었는가 |
| 규약 | 반드시 지켜야 하는 것 |
| 운영 | 띄우고 유지하는 법 |
| 기록 | 그때의 측정·판단. 고치지 않는다 |
| 진행 | 지금 무엇을 하고 있는가 |

## 4. 선언이 아니라 장치로

**이 프로젝트에서 가장 비싸게 배운 것이다.** 처음에는 09 문서에
"두 모드를 함께 챙긴다" 고 적어 두었는데, 적어 둔 것만으로는 한 번도 지켜지지 않았다.
프롬프트에서 배운 것과 똑같다 — **부탁하면 안 지켜지고, 강제하면 지켜진다.**

그래서 규약마다 그것을 지키게 하는 장치를 짝지었다.

| 규약 | 장치 |
|---|---|
| 문서 구조 (링크 · 머리말 · 색인) | `./dev.sh docs` |
| 추적 정합성 (체크된 태그는 DONE 에 세부가 있다) | `./dev.sh docs` |
| [09 모드별 차이](09-mode-matrix.md) 의 표 | `backend/tests/test_mode_matrix.py` |
| 두 모드 공통 동작 | `backend/tests/test_both_modes.py` |

**장치가 붙은 문서는 설명이 아니라 명세가 된다.** 09 의 값을 바꾸면 테스트가 깨지고,
고치려면 문서를 보게 된다. 머리말의 `강제` 칸이 그 짝을 가리킨다.

### 4.1 검사는 실패하는 것을 보고 믿는다

통과만 하는 검사는 없는 것과 같다. `./dev.sh docs` 의 네 검사는 각각
일부러 깨뜨려 잡히는 것을 확인했다 — 없는 링크, `위` 줄 삭제, 색인에 없는 문서,
끝나지 않은 태그를 `[x]` 로 바꾸기.

마지막 검사는 바로 쓸모가 있었다. M5 의 세부를 한 항목으로 묶어 적었다가
T1~T5 가 전부 걸려 태그별로 다시 썼다. **내가 세운 규칙을 내가 어긴 것을 검사기가 잡았다.**

## 5. 왜 추적을 셋으로 나누는가

[ROADMAP](plan/ROADMAP.md) · [ISSUES](plan/ISSUES.md) · [DONE](plan/DONE.md) 셋이다.

가르는 축은 **의도**다. 계획한 것은 ROADMAP 의 `M`-`T`, 하다가 드러난 결함은
ISSUES 의 `H`. 둘은 성격이 다르지만 **관리 방식은 같다** — 체크박스 + 태그 + 한 줄 요약.

- **상태는 체크박스 하나뿐.** 할 일 문서와 완료 문서를 따로 두면 한 작업이 옮겨갈 때
  두 곳을 고쳐야 하고, 반드시 한쪽을 빼먹는다.
- **끝나도 줄을 지우지 않는다.** 체크만 하고 요약은 남긴다. 마일스톤이 끝난 뒤에도
  무엇으로 이뤄졌는지 읽히고, 같은 문제가 다시 올라왔을 때 전에 어떻게 봤는지 찾을 수 있다.
- **세부는 DONE 한 군데에만.** 구조를 보는 문서와 기록을 보는 문서를 나눠야
  규모가 커져도 ROADMAP 이 한눈에 읽힌다.
- **DONE 은 무엇을 / 왜 / 어떻게 / 남은 것** 틀로 쓴다. **`왜` 를 강제하는 것이 핵심이다.**
  무엇을 했는지는 git log 에 있다. 왜 그렇게 판단했는지는 어디에도 없다.

번호는 전역 연번이고 **재사용하지 않는다.** 커밋 메시지·PR 제목·코드 주석이 태그를
주소로 쓰므로, 지운 번호를 다시 쓰면 링크가 조용히 썩는다.

## 6. CLAUDE.md 가 꼭대기인 이유

이 프로젝트는 LLM 에이전트가 주로 개발한다. 그래서 문서 계층의 꼭대기는
**세션마다 자동으로 읽히는 단 하나의 파일**이어야 한다. 그게 `CLAUDE.md` 다.
따로 `DEVELOPMENT-GUIDE.md` 를 만들면 아무도 — 사람도 에이전트도 — 열지 않는다.

자동으로 읽힌다는 것은 **매번 비용을 치른다**는 뜻이기도 하다. 그래서 두 규칙을 둔다.

- **규칙은 추상적으로, 예시는 따로.** 곡해하기 쉬운 것만 예시를 붙인다
  (예: 작업 진행 — 규칙 일곱 줄 + 예시 블록 하나).
- **구체적인 것은 아래로 위임한다.** 값·명령·파일명·프로바이더 차이는 하위 문서가 든다.
  CLAUDE.md 에는 원칙과 링크만 남긴다.

판별법이 하나 있다. **CLAUDE.md 를 고치고 싶어졌는데 규칙이 바뀐 게 아니라면,
그건 위임했어야 할 내용이다.** 코드 규칙의 구체는 [10 코드 규약](10-code-conventions.md) 으로,
명령 목록은 [README](../README.md) 로 내린 것이 그 예다.

## 7. 다른 프로젝트로 옮길 때

이 프로젝트에 남는 자산은 코드가 아니라 이 구조다. 옮길 때 무엇이 일반적이고
무엇이 여기 고유인지 갈라 둔다.

**그대로 가져갈 수 있는 것**

1. 단일 색인 + 모든 문서의 `위` 링크
2. 표준 머리말 다섯 칸 — 층 · 상태 · 읽어야 할 때 · 위 · 함께
3. 상태 어휘 셋 — 유효 · 기록 · 대체됨 (**기록은 고치지 않는다**)
4. 의도로 가르는 추적 — 계획(`M`-`T`) / 결함(`H`), 관리 방식은 동일
5. 구조·정합성 검사를 CI 에 묶기
6. 규약 문서마다 그것을 강제하는 테스트를 짝지우기

**갈아 끼워야 하는 것**

- **층의 이름과 수.** 여기서는 일곱이지만, 라이브러리라면 `공개 API` 층이,
  데이터 파이프라인이라면 `스키마` 층이 필요할 것이다.
- **꼭대기 파일.** 에이전트가 개발하지 않는다면 `CLAUDE.md` 가 아니라
  `CONTRIBUTING.md` 나 사내 위키의 한 장이 그 자리에 온다.
- **번호 체계.** 여기서는 코드 주석이 문서 번호를 주소로 쓰기 때문에 번호를 못 바꾼다.
  그 결합이 없다면 층별 접두사(`design-`, `ops-`)가 더 읽기 좋다.

**옮기지 말아야 할 것**

모든 규약에 장치를 붙이려 들지 않는다. 장치는 **실제로 어긋난 적이 있는 규약**에만 붙인다.
여기서도 `./dev.sh docs` 는 H-011 과 H-014 가 실제로 난 뒤에 만들었다.
어긋난 적 없는 규약에 검사를 붙이면 유지 비용만 늘고 아무도 믿지 않는다.
